# Task 1. Целевая архитектура и приоритизация проблем

Диаграмма контейнеров целевой архитектуры (через год):
`c4-container-target.drawio` (превью `c4-container-target.png`).

## 1. Как целевая архитектура поддерживает бизнес-сценарии

| Бизнес-сценарий | Что обеспечивает в целевой архитектуре |
|---|---|
| Быстрая подготовка отчётности по любым срезам | Портал самообслуживания (BI поверх Lakehouse): витрины уже рассчитаны в ClickHouse, сложные отчёты - секунды, а не часы; конструктор отчётов с семантическим слоем и RLS по уровню доступа |
| Целостное представление по ключевым показателям | Слой общих измерений (клиент, продукт, подразделение) и каталог данных с единым глоссарием; домены публикуют согласованные data products |
| Независимое развитие финтех-направления | Домен Fintech со своими сервисами (Go/Java), своей OLTP-БД и своим ЦОД-сегментом/облачным окружением; обмен через события в Kafka и API, а не через логику в DWH |
| Независимое развитие ИИ-направления | Домен AI с feature store и ML-платформой; медицинские данные остаются в домене Clinical и передаются ИИ-сервисам по API с псевдонимизацией |
| Подключение новых бизнесов (фармацевтика, электроника) | Интеграционная платформа: API Gateway + Kafka + стандарт data product; новый домен подключается по контракту за недели, без доработок DWH |
| Качество медицинских и финансовых сервисов | Разделение контуров: медицинские карты и исследования - только в Clinical (не попадают в витрину); финансовые данные - в Fintech с требованиями ЦБ; наблюдаемость и SLO на каждый домен |
| Миграция в облако, отказоустойчивость | Отдельные облачные окружения на домен, Kubernetes, managed-БД с репликацией между зонами, бэкапы, IaC (Terraform) |
| Снижение затрат на устаревшее оборудование | Вывод SQL Server 2008, PowerBuilder и Camel-ESB по шагам strangler fig; DWH остаётся временно только как источник исторических данных |

## 2. Проблемные места

| № | Проблема | Какие бизнес-сценарии страдают | Последствие |
|---|---|---|---|
| P1 | DWH на SQL Server 2008 содержит бизнес-логику всех направлений; любое новое направление требует доработок в DWH | подключение новых бизнесов, независимое развитие финтеха и ИИ | time-to-market нового направления - месяцы; очередь изменений в одной команде DWH |
| P2 | Сложные отчёты строятся часами: сотни ТБ, множество трансформаций, Power BI с кастомизациями поверх DWH | подготовка отчётности, управленческие решения | решения принимаются с задержкой в день и более; аналитики ждут, а не анализируют |
| P3 | SQL Server 2008 снят с поддержки: нет патчей безопасности, нет масштабирования, нет облачного managed-варианта | качество медицинских и финансовых сервисов, соответствие регуляторам, миграция в облако | риск инцидента ИБ и штрафов; невозможно перенести «как есть» в облако |
| P4 | Клиентский интерфейс операторов на PowerBuilder: устаревший стек, нет специалистов, десктоп-only | работа клиник, качество медицинского сервиса | дорогие и редкие доработки; невозможность работы с планшетов и в новых клиниках |
| P5 | Старая ESB на Apache Camel - единая точка интеграции и отказа; точка-точка связи через шину, нет контрактов и версионирования | интеграция финтеха, ИИ, новых партнёров | сбой шины останавливает все направления; каждая интеграция требует кода в шине |
| P6 | Медицинские карты, исследования и финансовые данные лежат в одном DWH вместе с отчётными данными | соответствие 152-ФЗ, 323-ФЗ, требованиям ЦБ; доверие клиентов | нельзя дать бизнес-пользователям самообслуживание без риска утечки спец. категории ПДн |
| P7 | Нет единого каталога и владельцев данных: показатели считаются по-разному в разных отчётах | целостное представление ключевых показателей | споры о цифрах на уровне руководства, повторные пересчёты |
| P8 | Нет data lineage и качества данных: ошибки в источниках обнаруживаются в отчётах | отчётность, качество финансовых сервисов | неверные управленческие и кредитные решения |
| P9 | Инфраструктура on-premise, нет IaC, ручное развёртывание | масштабирование, отказоустойчивость, снижение затрат | ресурсы под рост выделяются неделями; среды различаются |
| P10 | ИИ-сервисы получают медицинские данные через ESB напрямую из DWH без контролируемого контракта | ИИ-направление, регуляторные требования | нельзя ни быстро обновлять модели, ни доказать регулятору законность обработки |
| P11 | BI-система с большим числом кастомизаций: логика отчётов размазана между DWH и Power BI | отчётность, масштабирование отчётности на новые домены | каждый новый срез - доработка в двух местах |
| P12 | Нет отказоустойчивости и геораспределения; резервное копирование не описано | доступность медицинских и финансовых сервисов | простой клиники или банка при сбое оборудования |

## 3. Приоритизация

### MoSCoW (привязка к целям бизнеса)

| Приоритет | Проблемы | Обоснование |
|---|---|---|
| **Must** | P1, P2, P3, P6 | без выноса логики из DWH нельзя ни подключить новые бизнесы (выручка), ни ускорить отчётность (скорость решений); SQL Server 2008 - риск ИБ и блокер миграции в облако; разделение медицинских/финансовых данных - условие регулятора и условие самообслуживания |
| **Should** | P5, P7, P9, P12 | интеграционная платформа и каталог данных нужны, чтобы домены развивались независимо и показатели сходились; IaC и отказоустойчивость - основа облачного переезда |
| **Could** | P4, P8, P10, P11 | улучшают качество сервиса и скорость доработок, но могут идти поэтапно после Must/Should; PowerBuilder временно сохраняется в домене Clinic |
| **Won't (в этом году)** | полный вывод DWH; миграция всех исторических данных; замена Power BI | DWH остаётся источником истории до завершения доменов; Power BI сохраняется как один из клиентов портала |

### Матрица Эйзенхауэра

| | Срочно | Не срочно |
|---|---|---|
| **Важно** | P3 (снятый с поддержки SQL Server - риск ИБ), P6 (медданные в общей витрине - регулятор), P2 (отчёты часами - решения запаздывают) | P1 (логика в DWH - стратегическая развязка доменов), P5 (ESB), P9 (IaC и облако), P12 (отказоустойчивость), P7 (каталог) |
| **Не важно** | P11 (кастомизации BI - закрывается порталом) | P4 (PowerBuilder - заменить после Clinic-домена), P8, P10 (lineage, контракты ИИ - после интеграционной платформы) |

### Итоговый порядок

1. P3 + P6 - безопасность и регуляторика: изоляция медицинских и финансовых данных, вывод SQL Server 2008 из-под пользовательской нагрузки.
2. P2 + P1 - отчётность и развязка доменов: Lakehouse, витрины, портал самообслуживания; домены Fintech и AI получают свои хранилища.
3. P5 + P9 + P12 - интеграционная платформа, IaC, облачная отказоустойчивость.
4. P7 + P8 + P10 - каталог, lineage, качество данных, контракты с ИИ.
5. P4 + P11 - замена PowerBuilder, упрощение BI.
