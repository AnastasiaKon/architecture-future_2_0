# Task 4. Обоснование конфигурации Terraform

Диаграмма автоматизации развёртывания: `diagram.png` (исходник
`diagram.drawio`). Конфигурация описывает **окружение одного домена**
(в примере - Clinic, dev) в Yandex Cloud. Для каждого домена и окружения
запускается тот же код с другим `terraform.tfvars` и другим каталогом
(folder) - это и есть «шаблон домена» из Task1-3.

## 1. Что управляется Terraform, а что вручную

| Terraform (`main.tf`) | Вручную, один раз |
|---|---|
| VPC, подсети приложений и данных по зонам, NAT-шлюз, таблица маршрутов | облако и каталоги на домен/окружение (создаёт администратор организации) |
| группы безопасности app и data | сервисный аккаунт Terraform с ролью `editor` на каталог и его ключ (в секретах CI) |
| ВМ узлов приложений (по одной на зону), отдельные диски данных | назначение IAM-ролей: доступ сервисов домена к бакету и ключу KMS, версионирование бакета (`storage.admin`) - Terraform с ролью `editor` права не раздаёт |
| Managed PostgreSQL, база и пользователь | бакет и блокировка для remote state (bootstrap до первого `init`) |
| Object Storage bucket с SSE-KMS и ключ KMS | DNS-зона, сертификаты - общие для всех доменов |
| | Kubernetes-манифесты и приложения (ArgoCD/Helm, отдельный репозиторий); VPN/бастион |

Граница проведена так: всё, что **принадлежит домену и воспроизводится для
каждого домена**, - в коде; всё, что **общее для организации, нужно до
появления Terraform или раздаёт права** (state, ключ, каталоги, IAM), -
вручную и документировано. Так Terraform работает с минимально
достаточной ролью `editor` и не может расширить чьи-либо права.

## 2. Выбор ресурсов и параметров

Значения в `terraform.tfvars` подобраны под dev-окружение и квоты пробного
облака (на зону: 2 vCPU, 16 ГБ RAM, 20 ГБ HDD, 10 ГБ SSD; Managed
Databases: 2 vCPU на облако). Для prod меняются только значения переменных.

| Параметр | dev (`terraform.tfvars`) | prod | Почему |
|---|---|---|---|
| Зоны | `ru-central1-d`, `ru-central1-e` | 3 зоны | ВМ распределяются по зонам (`count.index % length(zones)`), отказ зоны не останавливает домен. В момент запуска зона `b` закрыта для новых ресурсов, `a` перегружена - поэтому `d` и `e`; смена зон - правка списка |
| Подсети app / data | /24 на зону | /24 на зону | приложения и managed-БД в разных подсетях: БД не доступна напрямую, правила SG проще; /24 - запас на рост числа узлов |
| NAT-шлюз + маршрут 0.0.0.0/0 | shared egress | так же | ВМ без публичных IP (`nat = false`) выходят к пакетам и внешним API через NAT; поверхность атаки минимальна, исходящий трафик централизован |
| SG app | 443 из `ingress_cidrs`, 22 из `admin_cidrs`, self | так же | снаружи только HTTPS (через балансировщик/шлюз), SSH только из VPN/бастиона, трафик между узлами домена - внутри группы |
| SG data | 6432 только из SG app | так же | PostgreSQL принимает подключения только от узлов приложений домена, а не по CIDR |
| ВМ `standard-v3` | 2 шт., 2 vCPU / 2 ГБ, `core_fraction = 20` | 4+ vCPU / 8+ ГБ, `core_fraction = 100` | узлы под сервисы домена (Docker / K8s-воркеры). В dev - минимальная стоимость и вписывание в квоту; в prod - гарантированные ядра для предсказуемой задержки |
| Загрузочный диск | `network-hdd` 10 ГБ | `network-ssd` 30 ГБ | ОС и контейнеры; образ Ubuntu 22.04 требует от 8 ГБ. HDD в dev - из-за квоты SSD 10 ГБ на зону |
| Диск данных | `network-hdd` 10 ГБ, `auto_delete = false` | `network-ssd` 100+ ГБ | данные отделены от ОС: ВМ можно пересоздать, диск останется; размер увеличивается без пересоздания |
| `vm_preemptible` | `false` | `false` | прерываемые ВМ дешевле, но для сервисов клиники недопустимы; флаг оставлен для sandbox |
| Managed PostgreSQL 16 | `s3-c2-m8`, `network-ssd` 20 ГБ, 1 хост | `s3-c4-m16`+, 2-3 хоста в разных зонах, `deletion_protection` | OLTP домена: управляемый сервис с ежедневным бэкапом (окно 02:00) и авто-failover при нескольких хостах; число хостов - переменная `pg_hosts`, хосты ставятся по зонам из `zones` |
| Object Storage + KMS | SSE-KMS AES-256, ротация ключа раз в год, анонимный доступ закрыт | + версионирование и lifecycle | снимки/исследования и data products домена шифруются ключом домена; бакет создаётся по IAM-токену Terraform без статических ключей |
| Пароль PostgreSQL | `TF_VAR_pg_password` | секрет CI / Lockbox | переменная `sensitive`, в репозиторий не попадает |

## 3. Почему декларативный подход

- **Описываем результат, а не шаги.** Terraform сам вычисляет порядок
  создания (сеть -> подсети -> ВМ -> БД) по зависимостям и показывает план
  до изменений: что создаётся, что меняется, что удаляется.
- **Идемпотентность.** Повторный `apply` с тем же кодом ничего не меняет;
  расхождение с реальностью (кто-то изменил вручную) видно в `plan`.
- **Ревью инфраструктуры как кода.** Изменение размера диска или добавление
  зоны - merge request с diff, а не тикет администратору.
- **Безопасные изменения.** Terraform знает, какие изменения требуют
  пересоздания ресурса, и предупреждает об этом заранее.

## 4. Как IaC обеспечивает воспроизводимость и масштабируемость

- **Воспроизводимость:** один и тот же код создаёт dev, stage и prod,
  различия - только в `terraform.tfvars`; окружение домена поднимается с
  нуля за минуты и всегда одинаково; DR-регион - тот же код с другими
  зонами.
- **Масштабируемость:** новый домен (Fintech, AI, партнёр) - новый каталог
  и новый `tfvars`; рост нагрузки - `vm_count`, `vm_cores`, `pg_preset`,
  третья зона в `zones`; код можно оформить модулем и вызывать для всех
  доменов из одного корня.
- **Прозрачность и аудит:** история инфраструктуры - история git; `plan`
  в CI показывает последствия до применения; state хранится централизованно
  с блокировкой, что исключает параллельные конфликтующие изменения.
- **Связь с остальной архитектурой:** `outputs.tf` отдаёт идентификаторы
  сети, адреса ВМ, FQDN PostgreSQL, имя бакета и ключ KMS - их потребляет
  репозиторий приложений (Helm values), поэтому инфраструктура и приложения
  связаны кодом, а не ручной передачей параметров.

## 5. Проверка

```bash
cd Task4
export TF_VAR_pg_password='...'           # пароль из секрета
# ключ сервисного аккаунта terraform-sa - в sa-key.json (в .gitignore)
terraform init                             # провайдер yandex-cloud/yandex ~> 0.130
terraform fmt -check && terraform validate # форматирование и валидность
terraform plan -out=tfplan                 # план создания ресурсов
terraform apply tfplan                     # создание; результат - apply.png
terraform destroy                          # удаление dev-окружения после проверки
```

Для `init` в РФ используется зеркало провайдеров Yandex Cloud
(`~/.terraformrc` с `network_mirror = https://terraform-mirror.yandexcloud.net/`).

Результат: `apply.png` - вывод `terraform apply`, `terraform state list`
(18 ресурсов) и `terraform plan` без изменений после применения.
При запуске упёрлись в ограничения облака: зона `ru-central1-b` закрыта для
новых ресурсов, `ru-central1-a` перегружена, квоты пробного облака малы
(2 vCPU и 20 ГБ HDD на зону, 2 vCPU на Managed Databases). Поэтому dev
запущен в зонах `d` и `e` с одним хостом PostgreSQL; код при этом не
менялся - только значения в `terraform.tfvars`, что и демонстрирует
воспроизводимость подхода. После проверки dev-окружение удалено
`terraform destroy`; ключ KMS удаляет администратор (у роли `editor` нет
права на удаление ключей).
