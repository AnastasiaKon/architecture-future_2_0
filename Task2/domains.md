# Task 2. Разделение на домены и потоки данных

DFD: `dfd-domains.drawio` (превью `dfd-domains.png`).

## 1. Домены

| Домен | Что внутри | Для какого бизнес-сценария | Команда и окружение |
|---|---|---|---|
| **Clinic** | пациенты, приёмы, медкарты, истории болезни, исследования и снимки; веб-интерфейс операторов (замена PowerBuilder) | работа клиник, качество медицинского сервиса; источник данных для ИИ | команда клиник; отдельное облачное окружение с усиленной ИБ (152-ФЗ, 323-ФЗ); OLTP PostgreSQL + Object Storage |
| **Fintech** | счета, кредиты, платежи, финансовая история; core banking; сервисы на Go/Java | банковские услуги, финансовая отчётность, кредитные решения | команда банка; отдельное окружение с требованиями ЦБ (152-ФЗ, 161-ФЗ, ГОСТ 57580); OLTP PostgreSQL HA |
| **AI** | ИИ-сервисы диагностики и рекомендаций (Python), feature store, ML-платформа | ИИ-анализ медицинских данных, новые ИИ-продукты | ML-команда; окружение с GPU; работает только с псевдонимизированными данными по API из Clinic |
| **Corporate (головной офис)** | персонал, инвентаризация, финансовая отчётность группы, управленческие показатели | консолидированная отчётность и управление группой | команда головного офиса; потребитель витрин, владелец общих измерений |
| **Partner-домены** (Pharma, MedTech) | сервисы и данные партнёра: продажи препаратов, телеметрия оборудования | интеграция новых бизнесов без доработок DWH | команда партнёра; домен создаётся по шаблону (Terraform-модуль + топики + стандарт data product) |
| **Платформа данных** (общая) | Kafka, API Gateway/IdP, Lakehouse, Airflow/dbt, каталог, витрины ClickHouse, портал самообслуживания | быстрая отчётность по любым срезам, целостная картина показателей | платформенная команда данных; обслуживает домены как внутренних клиентов |

Принцип: **операционные данные живут в домене-владельце**, в общую
платформу уходят только **data products** - подготовленные, описанные в
каталоге и очищенные от медицинских карт и исследований наборы. Логика
направления остаётся в домене, а не в DWH.

## 2. Потоки данных по бизнес-сценариям

**A. Интеграция нового финтех-сервиса.** Сервис развёртывается в окружении
Fintech, пишет в свою OLTP, публикует события в Kafka по схеме из Schema
Registry и dbt-модель data product. Airflow подхватывает контракт, витрина
появляется в портале. DWH и ESB не участвуют.

**B. ИИ для анализа медицинских данных.** Clinic по API через Gateway
передаёт в AI исследование под псевдонимом (без Ф. И. О. и истории);
AI возвращает результат в карту пациента по тому же API. В feature store
хранятся только псевдонимизированные признаки; в витрины уходят метрики
моделей, а не медицинские данные.

**C. Отчёт по любому срезу.** Портал обращается к витринам ClickHouse
через семантический слой; RLS ограничивает строки уровнем доступа
сотрудника; конструктор отчётов работает на общих измерениях (клиент,
подразделение, период, продукт).

**D. Новый партнёр.** Домен создаётся по шаблону: окружение, namespace,
топики, схема data product. Подключение занимает недели, платформа не
меняется.

**E. Legacy.** DWH переводится в режим read-only; история переносится в
Lakehouse через CDC (Debezium); оставшиеся интеграции ESB заменяются
адаптерами на события, после чего ESB выводится.

## 3. Аргументация разделения

| Преимущество | Как достигается |
|---|---|
| Ускорение вывода продуктов | команда домена меняет свои сервисы и data product без очереди к команде DWH; контракт - единственная точка согласования |
| Снижение зависимости от DWH | новая логика не пишется в SQL Server; DWH становится источником истории и выводится; отчётность строится на витринах |
| Независимое развитие направлений | у домена своё окружение, бюджет, релизный цикл и SLO; сбой или релиз одного домена не трогает другие |
| Соответствие регуляторам | медицинские и финансовые данные изолированы в своих доменах с собственными мерами ИБ; в общую витрину они не попадают по контракту и по тегам в каталоге |
| Масштабирование под новые бизнесы | домен-шаблон и стандарт data product делают подключение партнёра повторяемой процедурой |
| Целостная картина показателей | общие измерения и глоссарий в каталоге; показатель считается один раз в data product владельца |
| Производительность отчётности | трансформации выполняются заранее в dbt/Airflow, отчёт - чтение подготовленной витрины ClickHouse |

Компромиссы: дублирование справочных данных между доменами (решается
общими измерениями и событиями), необходимость платформенной команды и
дисциплины контрактов, временная двойная работа legacy и новых доменов.
