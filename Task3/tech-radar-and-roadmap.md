# Task 3. Технологический радар и роадмап

Радар: `tech-radar.drawio` (превью `tech-radar.png`). Кольца: **Adopt** -
используем/внедряем; **Trial** - пилотируем в одном домене; **Assess** -
изучаем; **Hold** - не развиваем, выводим.

## 1. Технологический радар

### Данные и аналитика

| Технология | Кольцо | Статус | Бизнес-сценарии |
|---|---|---|---|
| ClickHouse (managed) - витрины | Adopt | новое | отчёт по любому срезу за секунды; портал самообслуживания |
| Lakehouse: Object Storage + Apache Iceberg, Trino/Spark | Adopt | новое | хранение сотен ТБ с разделением compute/storage; история из DWH; масштабирование под новые бизнесы |
| Airflow + dbt | Adopt | новое (Airflow уже знаком по ИИ-направлению) | конвейеры data products доменов; трансформации заранее, а не в момент отчёта |
| OpenMetadata - каталог, lineage, теги | Adopt | новое | целостность показателей, владельцы данных, контроль ПДн в витринах |
| Great Expectations - качество данных | Trial | новое | качество финансовой и управленческой отчётности |
| Superset + семантический слой (Cube) | Adopt | новое | портал самообслуживания, конструктор отчётов, RLS |
| Power BI | Hold -> клиент портала | текущее | сохраняется для существующих отчётов, переключается на витрины |
| Data Mesh (домены владеют data products) | Adopt (как подход) | новое | интеграция новых бизнесов без DWH |
| Kafka (managed) + Schema Registry, Debezium CDC | Adopt | новое | события доменов, вывод ESB, перенос истории из DWH |
| DWH на SQL Server 2008 | Hold -> вывод | текущее | только история до переноса в Lakehouse |

## 2. Роадмап

| Этап | Срок | Шаги | Ожидаемый результат | Ответственные команды | Ресурсы |
|---|---|---|---|---|---|
| **0. Подготовка и согласование** | 0-2 мес | архитектурное решение (Task1-2), границы доменов, стандарт data product, облачный landing zone (Terraform: VPC, подсети, NAT, IAM, folders на домен), каталог данных, SIEM/KMS | решение согласовано; окружения доменов создаются из кода; домены знают свои контракты | архитектура, платформенная команда, ИБ | архитектор, 2 DevOps, 1 ИБ; облако: сеть, K8s, Vault |
| **1. Платформа данных и MVP портала** | 2-5 мес | Lakehouse + ClickHouse; Airflow/dbt; CDC из DWH (read-only копия); первые data products Corporate и Fintech; портал на Superset с RLS и 5-10 ключевыми отчётами | ключевые отчёты строятся за секунды; DWH больше не меняется под отчётность | платформенная команда данных, Fintech, головной офис | 3 data-инженера, 1 аналитик данных; managed ClickHouse, Object Storage |
| **2. Выделение доменов Fintech и AI** | 3-8 мес | Kafka + Schema Registry; Gateway/IdP; финтех-сервисы публикуют события и data product; AI получает данные из Clinic по API с псевдонимизацией; MLflow | новый финтех-сервис и новая модель выходят без изменений DWH; соответствие требованиям ЦБ и 152-ФЗ подтверждено | Fintech, AI, платформенная команда, ИБ | команды доменов; managed Kafka, K8s с GPU |
| **3. Домен Clinic и замена PowerBuilder** | 5-10 мес | сервисы клиники, Clinic OLTP с шифрованием полей, новый веб-интерфейс операторов; пилот в одной клинике, затем тираж; перенос логики из DWH | клиники работают в новом UI; медицинские данные изолированы в домене | команда клиник, платформенная команда, ИБ | 4-6 разработчиков, 1 UX; managed PostgreSQL, Object Storage |
| **4. Самообслуживание и партнёры** | 8-12 мес | конструктор отчётов, общие измерения и глоссарий, Great Expectations; шаблон домена; подключение Pharma и MedTech | сотрудник сам строит отчёт по любому срезу в пределах доступа; партнёр подключён за недели | платформенная команда, партнёры, головной офис | 2 data-инженера, 1 аналитик; Terraform-модуль домена |
| **5. Вывод legacy и отказоустойчивость** | 10-12+ мес | перенос истории в Lakehouse завершён; DWH и ESB выключены; PowerBuilder выведен; DR-регион, учения по восстановлению; FinOps | затраты на устаревшее оборудование сняты; RTO/RPO критичных систем подтверждены | платформенная команда, DevOps, ИБ | DevOps, DBA; резервный регион |

Критически важные меры для качества медицинских и финансовых сервисов,
идущие сквозь все этапы: SLO и наблюдаемость на каждый домен, аудит
доступа к данным в SIEM, шифрование медицинских и финансовых данных,
резервное копирование и регулярные тесты восстановления, Privacy/контракт
гейты в CI/CD.

## 3. Обоснование этапов

| Этап | Зачем бизнесу | Влияние |
|---|---|---|
| 0 | без согласованных границ доменов и стандарта data product команды продолжат писать логику в DWH; landing zone в коде даёт одинаковые и безопасные окружения | масштабируемость: окружение домена - за часы; ИБ - с первого дня |
| 1 | самая болезненная проблема - отчёты часами; витрины и портал дают быстрый измеримый эффект и снимают нагрузку с DWH | скорость решений: отчёт за секунды; затраты: DWH не дорабатывается |
| 2 | финтех и ИИ - направления роста; им нужна независимость и регуляторная чистота раньше остальных | time-to-market новых финансовых и ИИ-продуктов; качество - контролируемые контракты, псевдонимизация |
| 3 | клиники - ядро бизнеса; PowerBuilder и логика в DWH тормозят открытие новых клиник | качество медицинского сервиса, работа с планшетов, изоляция медданных |
| 4 | самообслуживание убирает очередь к аналитикам; шаблон домена делает подключение партнёров повторяемым | масштабирование на новые бизнесы без роста платформенной команды |
| 5 | legacy стоит денег и несёт риск ИБ; DR нужен банку и клиникам | снижение затрат на поддержку; доступность сервисов |
